# Leonidas: gotchas and session notes (read on demand)

Moved out of [agent-playbook.md](../agent-playbook.md) so it is not loaded every turn. Search it before touching updater, release, rebrand, worktree, build-preflight or quota code.

## Gotchas already paid for

- **A bulk rebrand can miss variants (2026-11-06):** check uppercase queries, URL-encoded names, slugs, process matchers and installer filenames. Keep installed credential service names, scheduled task ids and the old CLI shim marker until a migration handles them. A matching baseline failure is still a failed check when the task requires every check to pass.
- **Windows pins need a stable launch path (2026-11-06):** keep the installed executable basename during a rebrand. electron-builder omits the keep-shortcuts argument if the new executable path does not exist before uninstall. That removes existing pins. Use productName and shortcutName for visible branding.
- **Shortcut icons need a new resource path (2026-11-06):** an existing pin and desktop shortcut can retain the cached old icon after replacing the executable. Update their icon references in place to a version-specific icon, then notify the shell. Test the closed pin and desktop shortcut after the update.
- **A saved pin name and its hover text can differ (2026-11-06):** rename the existing shortcut file and notify the shell. Windows can keep the old closed-pin hover text until the next sign-in. Both graceful Restart Manager shutdown modes returned 351 in Sandbox. Do not claim an immediate refresh from a file rename alone. [Chromium documents the same cache limit](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/web_applications/os_integration/web_app_shortcut_win.cc#460).
- **Patch comments affect the lockfile (2026-11-06):** a rename inside patches changes its hash even if runtime behavior stays the same. Update all lockfile references and prove a frozen install passes.

- **Build Windows installers from the Visual Studio shell (2026-11-06):** Git's GNU `link.exe` can hide the MSVC linker. Load the Visual Studio developer shell before building the resource monitor and installer. In a disposable Windows Sandbox, use the mock update server to test the published old installer against the new build. Wait for the installer process itself; waiting for its child processes can hang on the Scribe engine.

Run cargo from a `.cmd` file that calls `C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools\VC\Auxiliary\Build\vcvars64.bat`, removes `C:\Program Files\Git\usr\bin;` from PATH, then runs `cargo test --quiet` in `services/scribe-engine`.

### Older gotchas

- **Watchdog forcefully crashing the renderer causes an infinite reload loop (2026-10-19):** RendererHangRecovery.ts pinged the renderer every 5 s and called webContents.forcefullyCrashRenderer() after 30 s of silence. Under normal load (initial rehydration, history rendering, GC) the renderer's V8 thread pauses or misses pings, triggering the crash. Each crash forces a reload, which incurs another heavy boot, causing another timeout after the 3-minute cooldown, looping forever. Retired: renderers must not be forcefully crashed by a timer.

- **The dev app hung on the loading screen for ever (found 2026-10-16):** the `Leonidas Code Dev Server` scheduled task ran at Windows priority 7 (below normal). Vite and its dependency optimizer starved at 0% CPU and never answered. The same start from a normal session took 10 s. `Install-DevShortcut.ps1` now sets `-Priority 4`. Other causes fixed the same day: `@clerk/clerk-js` in `optimizeDeps.include` does not resolve in `apps/web` (now filtered), React Compiler ran in dev (now build only, `LEONIDAS_DEV_REACT_COMPILER=1` turns it on), and `dev-live` was 1,453 files behind main (the supervisor now syncs it after 20 s of quiet in main). The boot splash in `apps/web/index.html` now shows progress, Retry and a copyable fix prompt for an agent.
- **A new RPC method needs 4 entries, not 2:** besides `rpc.ts` and the `ws.ts` handler, add it to `apps/server/src/auth/RpcAuthorization.ts` and `apps/server/src/observability/RpcInstrumentation.ts`. Without them the server rejects the call and the page shows its empty state with no error. The server typecheck reports the gap, so read every `error TS` line, not only the ones in the folder you changed.
- **The dev app's scheduled task can stall before it starts the runner:** in October 2026 `Leonidas Code Dev Server` sat for more than 15 minutes with no child process, while the same `Run-LeonidasDevServer.ps1` started at once from a normal session (`Start-Process pwsh -WindowStyle Hidden -File ...`). ## Why it is this way

- **`dev` is a derived local branch, never pushed:** the dev copy mirrored the main checkout, so feature branches and publishes never reached it. `dev` = origin/main plus clean branches, rebuilt from scratch each time and moved only when the gate is green (bisect to the culprit, drop it, hold the last good tip after 3 drops). Mixed-session branches stay out until a person or agent resolves them in `C:/lcw/dev-rebase`; `git rerere` keeps each resolution.
- **Native tasks and release planning:** Leonidas owns new tasks; Todoist supplied public interaction references. Agent execution requires explicit delegation. Existing AIOS cards and GitHub sharing remain compatible. Release scope lives in [`project-roadmap.json`](./project-roadmap.json); V1.0 remains an explicitly approved public launch.
- **Roadmap task identity:** Imported briefs carry a durable `Roadmap key:` in their descriptions. Renaming or moving a task must not reimport it. Use the shared `observeResize` helper for map connectors; raw ResizeObserver callbacks fail scoped lint.
- **Reuse electron-updater over a git-pull updater:** installed apps cannot `git pull`; the existing GitHub Releases path needs only a CI workflow. Card: [`t3-code-push-to-update-release-pipeline`](../../tasks/t3-code-push-to-update-release-pipeline.md).
- **Thin rebrand layer:** every branding touch makes `upstream/main` merges harder. Card: [`rename-the-t3-code-mcp-server-and-tools-to-leonidas-names`](../../tasks/rename-the-t3-code-mcp-server-and-tools-to-leonidas-names.md).
- **After an upstream merge, rename new upstream MCP tools:** the MCP server is `leonidas` and every tool starts with `leo_` (task `rename-mcp-server-leo`). A new upstream tool arrives as `t3_x` or `x`. `apps/server/src/mcp/McpToolNames.test.ts` fails until you rename its `Tool.make` string, its handler key and its mentions to `leo_x`. Old names for the 95 renamed tools stay valid in saved chats through `LEGACY_MCP_TOOL_NAMES` in `packages/shared/src/mcpServerName.ts`; do not add new tools to that list. Remove the alias layer (`LegacyToolNames.ts`, `renameLegacyToolCalls`, `toCurrentMcpToolRule`) two releases after it ships.
